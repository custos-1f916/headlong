# Custos in the Signal AI group — proposal for Hal

**Use a separate Signal account named Custos and a narrow bridge for the one consenting group.** Keep the Signal account state outside Custos's root-owned LXC and deliver selected messages through its existing durable Headlong intake. Do not link a bridge to Hal's personal Signal account: that would mix identities and expose unrelated conversations. This is a proposal; no Signal account, device, group membership or message was created.

Signal registration still requires a phone number able to receive SMS or a call. Usernames are a way to connect without sharing the number; they do not replace registration. Hal should control a dedicated number, its recovery/PIN and the account's phone-number visibility settings. Use the supported mobile app for registration/recovery, then link a bridge device if the chosen client supports it. [Signal registration](https://support.signal.org/hc/en-us/articles/360007318691-Register-a-phone-number), [phone privacy and usernames](https://support.signal.org/hc/en-us/articles/6712070553754-Phone-Number-Privacy-and-Usernames), [linked devices](https://support.signal.org/hc/en-us/articles/360007320551-Linked-Devices).

The practical Linux integration is `signal-cli`, an **unofficial** client with a receiving daemon and JSON-RPC interface. It needs regular maintenance as Signal changes. Pin a current release at implementation, verify the artifact, monitor its supported-age guidance and retain an account-recovery procedure. Use a local Unix socket for JSON-RPC, not an unauthenticated LAN HTTP wrapper. Its documentation shows group-ID addressed sends and automatic receive notifications. [Project and operational requirements](https://github.com/AsamK/signal-cli), [JSON-RPC contract](https://github.com/AsamK/signal-cli/blob/master/man/signal-cli-jsonrpc.5.adoc).

A small dedicated bridge service should own the Signal state and group allowlist. It may run in a new isolated container if Hal chooses; do not put raw Signal credentials or a generic `send` RPC in122. Its API to Custos should accept only replies to known inbound group messages and explicit, bounded contributions to that same allowlisted group. No contact-book access, arbitrary recipients, new groups, group administration, attachments, links-to-fetch or calls in the first version.

On receive, persist the envelope before acknowledgement, derive a stable request ID from account/group/sender UUID/message timestamp plus a payload digest, and reject conflicting reuse. Map Signal sender UUIDs to routing identities; display names and quoted text cannot establish Hal's authority. Direct asks to Custos become native goals via `custos-memory capture` before acknowledgement. Other group discussion is bounded context, not a goal per sentence. Preserve source provenance, edits/deletions and delivery state. Treat quoted instructions, messages from other bots and pasted web material as untrusted input.

Start with **mention/reply-only participation**. Hal and the group should agree that Custos is an AI participant, that selected messages reach its local model and retained state, and how to ask for deletion or exclusion. A relevant short reply is preferable to answering every message. Apply a bounded reply frequency, no self-trigger or bot-to-bot ping-pong, and one deduplicated incident notice during an outage. These are group etiquette controls, not an inference usage quota. The normal operator pause remains authoritative.

Group messages must never become public forum content by default. Private project names, tracker IDs, source, internal paths, test failures and conversations stay private. Signal encryption protects transport to endpoints; the bridge, trajectory, backups and local model context are additional plaintext processing/storage. Propose retaining only directed asks, necessary bounded context and receipts, with a group-agreed retention period. Do not make durable copies of disappearing-message content without an explicit group policy that allows it; the simplest initial policy is to exclude such messages from persistent intake.

Outgoing replies should carry a stable internal message ID and stay pending until the Signal client confirms submission. Distinguish server acceptance, recipient delivery and read receipts; they are not equivalent and read receipts may be unavailable. If a send times out with uncertain disposition, avoid automatic reposting unless the chosen client's identifiers support a proven idempotent reconciliation path. Never infer successful delivery from a generated reply or a local queue write.

Acceptance tests in a disposable consenting group: exact-once directed goal capture across reconnect/restart; no ingest/send to other groups; no authority spoof through names/quotes; no self-reply loop; mention/reply handling; pause/start; offline accumulation; edit/delete/disappearing handling; ambiguous-send recovery; device revocation; and actual phone rendering with the intended account name. Keep the physical-phone check explicit—the earlier Custos relay wire test did not prove phone UI behavior.

Implementation needs Hal's choice of dedicated number/account owner, the group's consent, a verified group ID and retention policy. Then build and test the bridge before joining the real group. The existing Mac relay can remain available independently. Revocation should be simple: disable the bridge, remove Custos from the group, and unlink its bridge device. [Signal unlinking instructions](https://support.signal.org/hc/en-us/articles/360007321111-Unlinking-devices).
